# Grays Harbor Crab Harvest Estimation: Pooled CPUE Model

## Development history

- **Companion to:** `BSS-GH-pooled-CPUE-model-documentation.md` (the published Method v1.0 reference).
- **Scope:** the full version-by-version change log of the pooled-CPUE pipeline and its Stan model, plus the detailed working notes from the convergence-debugging effort. Method v1.0 corresponds to pipeline code **v7.4**. Code **v7.5** (2026-07-10) adds the pooled backlog fixes POOL-2/4/5/6; because POOL-2 (incomplete-trip filter, default on) changes the shore estimate, Method v1.0's published numbers must be refreshed by a v7.5 re-run. Code **v7.6** (2026-07-10) then implements POOL-1 + POOL-3, moving the boat onto the gear-deployment scale; this moves the publication boat number too, so v7.6 must be re-run before the totals are trusted. Code **v7.7** (2026-07-11) moves the shore component onto the gear-deployment scale as well (POOL-7), so both fitted components now run on gear-deployments; it moves the publication shore number, so v7.7 must be re-run before the shore total is trusted. Code **v7.8** (2026-07-11) is a behavior-preserving repository refactor (helper functions extracted into `03_R_functions/`; all user toggles centralized into `run_config.R`) together with one number-moving completion fix: the pooled `run_pe` shore branch, which had been left on crabber-hours after v7.7, is ported onto the shared effort module so the shore PE matches the shore BSS unit. Code **v7.9** (2026-07-12) restructures `run_config.R` into the base parameter set, moves the per-population AR-resolution map into it, and tightens the pooled divergence-fraction backstop to 0.05 (P5/P7), with no estimate change. The current state is v7.9 plus the nine-item **Tier-2 + parity batch** (2026-07-13), validated by Run 1 (the authoritative run: pooled default, port total BSS 83,035) and cross-checked by the gear-resolved Run 2; that batch adds the pooled Stan terms `B2_C` / `B3` / `gamma_C` and the PE empty-stratum fallback among nine items, all detailed in the newest version-log entry and in `development_notes/PIPELINE_STATUS.md`.
- **Convention:** no em dashes.

This file is the provenance record for the pooled model. The published method document summarizes this history in one screen (its Section 19) and refers here for the detail. Entries are newest-first. The model's first published, operationally-frozen state is Method v1.0 (code v7.4); the entries below trace how it got there, from the post-critique baseline (v6.0) through the convergence work (v6.1 to v7.0) and the diagnostics and cross-validation additions (v7.1 to v7.4). Earlier shared milestones (v1 to v5) are summarized at the end and in `README.md`.

A note on numbering: these version tags (v6.x, v7.x) are the internal development tags carried in the driver's header and in the Stan model headers. They are distinct from the published "Method v1.0" label, which names the frozen method rather than a code revision. Method v1.0 = code v7.4.

### 2026-09-04, The AR escalation ladder becomes a production toggle, and the project context that reframes it (branch `OSP-boat-count-incorporation`)

Harness **303 assertions**, 0 failing. Details in `development_notes/PIPELINE_STATUS.md` Section 1h.

**CONTEXT NOW RECORDED IN THE CODE.** WDFW has published no estimate from this pipeline; `main` is the pre-FW-creel-meeting, pre-OSP state. There is no published figure a change has to stay consistent with, so continuity with an earlier internal run is not on its own a reason to prefer a modelling choice. The OSP stream is, per day, total returning vessels and the fraction that were CRABBING ONLY, which excludes combo trips that also crabbed and is therefore a LOWER BOUND on crabbing vessels rather than the crabbing fraction `f`; that is what `osp_crab_lower` / `f_lower` exist for. Both facts are now at the top of `run_config.R` and `CLAUDE.md`, where an operator or an agent will actually meet them.

**THE LADDER ALREADY EXISTED; WHAT IT LACKED NOW EXISTS.** `ar_escalate` gained a per-population and per-sub-season scope (`TRUE`, `c("shore")`, or `list(shore = "all_gear")`), because every rung is a multi-hour fit and two components already have known answers. `ar_escalation_log.csv` now keeps EACH RUNG'S OWN ESTIMATE and 95% interval rather than only its sampler diagnostics: the estimate used to be discarded when `fit` was overwritten, which meant the one thing a ladder exists to show, how the answer depends on resolution, was the one thing not recorded. The HTML report tabulates it with the reported rung marked. `ar_escalate_stop` adds an `"all_rungs"` diagnostic mode alongside the default `"first_pass"`, which is byte-identical to the previous behaviour.

**THE LIMIT, stated because it bounds the mechanism.** The ladder escalates on the CONVERGENCE gate. On the 2026-08-31 production run every component passes that gate, shore all-gear at daily included, so the production rule applied to this season changes nothing; that same fit carries p_loo at 35.2% of n_obs, 41 Pareto k above 0.7 and coverage_50 0.701 against a nominal 0.500, all invisible to the gate by construction. Making the ladder react to adequacy is a change to what the gate tests, not a setting.

**SELECTING BY THE NARROWEST INTERVAL WAS TESTED AND IS NOT THE DEFAULT.** On the boat 2x2 the two MISCALIBRATED cells have the narrowest relative intervals (142.4% and 146.6% against 153.7% and 156.0%), because a latent process that absorbs observation noise reports a tighter interval. On absolute width the calibrated cell wins, but catch and width are nearly proportional (ratio 0.64 in all four cells), so the criterion is close to "smallest estimate" and would bias the harvest number down. `"narrowest_pi"` is available for breaking a tie between rungs that are already adequate; it cannot decide adequacy.

**BATCH SIMPLIFICATION.** The 2026-09-03 batch replaced three forced rungs with one run of the production toggle: 7 fits instead of 12, one output folder, 17-20 h instead of 23-26 h, and it exercises the mechanism a future season will use rather than an experiment-only `ar_force` override.

**PE / BSS INCOMPLETE-TRIP ARM ALIGNMENT, and it is closed.** `prep_bss_crab_pooled.R` builds the `R_G_boat` frame from `int_d` AFTER `filter_incomplete_trips`, so the BSS behaves like the four-arm diagnostic's "exclude" arm; both Point Estimators built the same ratio from the UNFILTERED set, i.e. "gear_only". `sensitivity_incomplete_trips.csv` has reported that disagreement since 2026-08-25 as `production_arm_bss` against `production_arm_pe` without anyone acting on it. A CONSISTENCY fix rather than an accuracy one, and worth making precisely because it is small: there is no estimate to defend, only an inconsistency to remove. It is one helper and not two edits because the gear-resolved PE's comment already claimed it matched the BSS's `R_G_boat` while it did not, which is what two copies of one rule produces.

**ZERO-INFLATED CATCH LIKELIHOOD, prototype, ships OFF.** `crab_bss_pooled.stan` gains `zi_catch`, `zi_catch_prior_a/b` and `vector<lower=0,upper=1>[zi_catch] theta_C`, the same zero-size guard pattern `shared_tau` and `f_lower` use, so the OFF path leaves the unconstrained parameter vector unchanged. The target was chosen from the 2026-09-01 zero bin rather than from taste: shore all-gear 676 observed zeros against 605.4 expected (z = +3.8 on n = 1,649), shore pot closure 146 against 118.5 (z = +2.9), every BOAT stream inside |z| = 2.3. Three things are worth knowing about the implementation. The generated-quantities `log_lik_catch` mirrors the fitted mixture exactly, because a log_lik computed under a different likelihood from the one fitted makes every `elpd_loo` comparison meaningless and an elpd comparison is the entire basis on which this will be judged. **The season total is scaled by (1 - theta_C)**: `lambda_C` is fitted to the non-inflated component and rises to absorb the zeros `theta_C` removed, so an unscaled total would be inflated by 1/(1 - theta_C) purely as an artefact of enabling the feature. And `zi_catch` is set PER FIT from `catch_zi_populations` (default `"shore"`), so a single run carries the shore fits as treatment and the boat fits as an untouched negative control at no extra cost. The model compiles to C++ in 3.1 minutes.

**THE BATCH.** P1 (PE only, seconds) then G1 (gear track with the 2026-09-02 boat all-gear sampler fix, ~35 min, restoring a cross-check that has read 51,385 instead of about 70,900 since the fix lived only in an experiment flag), then Z0 (ZINB code present and OFF: the behaviour-neutrality gate AND the AR ladder's daily rung, so the ladder does not compare three post-edit rungs against a pre-edit production run), then A1-A3 (shore all-gear forced to weekly, biweekly and monthly), then Z1 (ZINB on the shore).

**The shore AR ladder is the main event.** Production fits that component at daily and on the 2026-08-31 production run it is the worst-behaved fit in the run: p_loo 35.2% of `n_obs` against the boat's 8.0%, 41 Pareto k above 0.7 against 1, and `coverage_50` 0.701 against a nominal 0.500, which is +7.1 sampling SDs. The gear-resolved track fits the same component at monthly and gets 0.035, -16.4 SDs. Both ends are bad, the middle has never been run, and the component is 29% of the port total. The ladder is read in the order that settled the boat 2x2: coverage from the randomized PIT first, then `p_loo` as a fraction of `n_obs` with the Pareto k count, then the CATCH stream's elpd, because the boat's daily AR improved the effort stream while making the catch stream worse and catch is what the harvest estimate is made of.

A flag that fires on everything carries no information.

The first attempt read it off the PIT at the observed zeros, which is a different question: those days are selected for being zero, so they are the low-mean days whose P(Y=0) is high by construction, and it read a calibrated trailer stream as 20% observed against 45% implied.

### 2026-08-31, The Stage 5 batch: the tau x AR 2x2 is settled, and the adequacy table it shipped with was wrong (branch `OSP-boat-count-incorporation`)

Six stages, 24 h of fitting, 11 of 12 criteria passing. Full review in `development_notes/stage5-batch-review-2026-08-31.md`. Harness at **199 assertions**.

**The 2x2.** Private-boat all-gear across `shared_tau` x boat AR: 25,868 (off/monthly), 31,008 (on/monthly), 37,359 (off/daily), 42,344 (on/daily). The interaction is **-155** against main effects of +5,140 and +11,491, so the two levers are additive: they act on different parts of the model and either could be adopted without the other. Additivity settles the arithmetic and adjudicates nothing.

**What adjudicates.** The shared turnover buys 14.7 nats of trailer elpd for 3.1 effective parameters (4.7 nats each), costs the catch stream 0.1 nats, adds no Pareto k above 0.7, and moves PIT mean, PIT sd and coverage all toward nominal. The daily boat AR buys elpd by spending 27 to 48 effective parameters on 195 observations, makes the CATCH stream 3.8 nats worse in both tau conditions, produces 2 then 16 bad Pareto k, collapses both observation-error scales (`sigma_r_OSP` 0.806 to 0.086; `sigma_r_E` 0.934 to 0.306), drives `r_OSP` to 133.7 with a 95% upper bound of 43,875, and pushes `phi_E` to 0.886 at daily resolution. Identification versus absorption, no longer a hypothesis. **Recommendation: adopt the shared turnover boat-only; do not adopt the daily boat AR.**

**Cross-track corroboration, the strongest the project has produced.** Raising the gear track's boat all-gear fit to the pooled track's adaptation as well as its draw count moved `tau_bar` from n_eff 49 / R-hat 1.081 / 554 divergences / gate REJECTED to n_eff 19,292 / R-hat 0.9997 / 2 divergences / BSS. Draws rose 2.5x and n_eff rose 394x, so draw count was never the binding constraint; the gear driver simply had no per-fit override for that component and ran it at `adapt_delta` 0.90 where pooled runs 0.99. The two tracks now agree on `tau_bar` to **0.03%** (2.5969 vs 2.5962), the boat component to 0.80% and the port total to 0.89%. The independent OSP/trailer overlap calibration puts the turnover at 2.01-3.03; the monthly posterior straddles it at 2.597 [2.06, 3.25], while the daily cell's 3.232 [2.87, 3.63] sits at or above its top.

**The adequacy table added on 2026-08-30 was inadequate, and this batch is what showed it.** `pit_worst_bias` ranked the (tau ON, daily) cell as the best-calibrated of the four when it is the worst: a latent process with one state per observation interpolates the data and piles every PIT value at 0.5, so the mean reads 0.495 while 98% of OSP observations fall inside a nominal 50% predictive interval. `cov50_worst_dev`, `pit_sd_worst_dev` and `flag_miscalibrated` are now in the table; both underlying statistics were already being written to `ppc_calibration_*.csv` and neither reached it. A second gap: `disp_neff_min` asks whether a dispersion parameter SAMPLED well, not whether it COLLAPSED, and `sigma_r_OSP` fell to 0.086 while holding n_eff 657, above the gate's floor. `disp_scale_min` is now reported and deliberately NOT flagged, because the half-Cauchy priors have no finite SD so contraction is undefined for them and any cut-off would be a number chosen after seeing these runs.

**One regression, found and fixed.** `tau_bar` was registered in the prior-vs-posterior table under its bare name while rstan summarises it as `tau_bar[1]` (declared `vector<lower=0>[shared_tau]`). `has_par()` strips the index and selected it, `post[pn, ]` then threw, and the writer's enclosing `tryCatch` swallowed the error, silently dropping the ENTIRE boat `prior_vs_posterior_*.csv` from S2, S3 and S4b. The entry is now named `tau_bar[1]` like `mu_mu_E[1]`, the row lookup tolerates a scalar/vector mismatch in either direction, and an unresolvable parameter is dropped rather than taking the file with it. The generalisable lesson: a `tryCatch` around a whole writer turns a one-row bug into a missing file.

**Also settled.** The empty-stratum re-run reproduces the driver exactly (zeroed days 44/0/47/9, PE catch to the crab), and `day_type` raises the PE 22.9-28.5% per component, +14.0% at the port; the decision is still open. The boat pot-closure AR re-run gives 735 at biweekly against the gear track's 743, with the all-gear component back at rung 4's 25,868, confirming the 2026-08-28 `ar_force` leak, which was worth 3,025 crab on that component, is closed.

**Two open items this batch created.** The trailer stream is over-covered in EVERY configuration (`coverage_50` 0.667-0.692 at monthly against a nominal 0.500, which is 4.6-5.3 sampling SDs at n = 195); the shared turnover improves it and nothing fixes it. And `prior_influential` measures variance reduction only: `tau_bar` contracts 0.216 and would be flagged prior-influential while its posterior mean sits 3.5 prior SDs from the prior mean.

### 2026-08-30, Stage 5 prerequisites: an informed-day floor, adequacy beside the gate, four reporting fixes, and a sanctioned way past the config merge (branch `OSP-boat-count-incorporation`)

No estimate changed. Everything here is code and reporting, applied before the Stage 5 batch (`06_diagnostics/run_stage5_2026-08-30.R`) so the batch has something exact to gate on. Harness: **178 assertions**, 0 failing.

**1. The informed-day floor on `shared_tau` (plan 5.2).** `bss_shared_tau_data()` gained `n_informed` and refuses the feature below `shared_tau_min_obs` (default **15**), falling back to per-day draws with a printed reason, exactly as the existing turnover guard does. Informed days are the I/E days plus, when `osp_scale_is_tau = 1`, the OSP days, because that is what puts `L` into a likelihood. Both preps compute the count and expose it on `stan_data`; `fit_data_summary.csv` records it with the resulting `shared_tau` so the decision is auditable from the output folder. The counts are 4 / 0 / 130 / 18 across the four fits, so any threshold in 5..18 separates the shore from the boat; 15 sits just below 18 on purpose, to keep the boat pot closure whose `tau_bar` (1.873 pooled, 2.050 gear) is corroborated across tracks. `shared_tau` stays **off in production**.

**2. Model adequacy, reported and deliberately not gating (plan 5.5).** New `03_R_functions/bss_model_adequacy.R` writes `model_adequacy.csv`: `p_loo` as a fraction of `n_obs` (worst stream), Pareto k > 0.7 count, worst PIT bias, and the smallest `n_eff` among the observation-model dispersion parameters, which the gate never inspects. Decoupled dispersion parameters are excluded from that minimum. `pass_convergence` is untouched: six configurations already passed every gate criterion while spanning 44% on the boat, and the point is to make "sampled" and "adequate" visibly different questions, not to quietly add a fifth gate.

**3. A retro path for both audit tables.** `annotate_model_adequacy_run()` and `annotate_decoupled_run()` rebuild adequacy and decoupling for an archived run folder from its own committed CSVs, writing `model_adequacy_reconstructed.csv` and `decoupled_audit.csv` beside the originals. Committed outputs are never rewritten and every reconstructed row says so. Both live and retro adequacy go through one shared body (`.bma_core`), because a reconstruction that computed its numbers slightly differently from the live writer would be worse than none, given the two get quoted side by side.

**4. Four reporting defects.** `pe_vs_bss_comparison.csv` now carries `bss_reported`, so a rejected fit's BSS column cannot read as a result (the 2026-08-29 gear run printed `BSS_catch = 32,689` beside `method_selected = "PE"`). `structural_params_*.csv` gained `fit_method` and an `estimate` column that is `median` with decoupled rows blanked, which covers `kappa_OSP` (prior-only in every fit under `osp_scale_is_tau`) and shore `r_OSP` (posterior mean 2.5 million). The pooled `expansion_ratios.csv` gained `R_G_boat_decoupled` and a `[PRIOR ONLY: no boat count stream in this fit]` suffix. The 2026-08-26 baselines, which have no `decoupled` column at all, are covered by the retro annotator, which marks window-dependent rules `unknown` rather than guessing them. A fifth, caught in review: the new writers had invented `"PE (gate fail)"` where `convergence_report.csv` says `"PE (convergence fail)"`, so one fit would have read two ways in one folder; all three now quote `gate_info$method_selected`, the gate being the single authority on method selection.

**5. `bss_sampler_override`.** Each driver merges `params_model` on top of `run_config`, so `params_model` wins every sampler key and a `run_config` delta on `bss_iter_default` does nothing while looking as though it complied. That is the `bss_min_interviews` trap again, and it would have silently voided plan 5.2's request to give the gear track more draws. The new list is applied after the merge, accepts sampler keys only, prints every change, and **errors** on anything else. Production value `NULL`.

**One thing measured rather than argued.** Extra elements in `rstan::stan(data = )` are inert: a two-chain fit with and without three added elements, including the new `.n_L_informed`, returned bit-identical draw matrices. The dotted metadata the preps attach to `stan_data` therefore cannot perturb a bit-identity gate, which the Stage 5 S2 gate depends on.

### 2026-08-26, Blocking defect in the 2026-08-25 batch: five Stan data variables declared but never passed (branch `OSP-boat-count-incorporation`)

The 2026-08-25 batch was run through its own validation ladder (`06_diagnostics/run_patch_validation_2026-08-25.R`) and **every one of the six model-runs failed on its first BSS fit**, on both tracks and in every configuration, with `dim(X) must have a positive length`. No fitted results were produced; the partial folders under `05_output/20260825/` are scratch.

-   **Cause.** `crab_fraction_stan_data()` returns 17 fields. `prep_bss_crab_pooled()` and `prep_bss_crab_gear()` copy them into the Stan data list one at a time, and five were never copied: `OSPF_n`, `osp_f_stratum`, `osp_f_total`, `osp_f_crab`, `osp_f_kappa_prior_mu`. Improvement 8 puts the per-day OSP likelihood behind `if (osp_crab_lower == 1)`, but the DECLARATIONS in the `data` block are unconditional and cannot be otherwise, so Stan threw `Exception: variable does not exist; processing stage=data initialization; variable name=OSPF_n; base type=int` on every fit regardless of `use_osp_crab_lower`. That is why the pre-patch-equivalent baseline rung died identically to the shipped-config rung.
-   **Why the reported error named something else.** rstan does not raise a data-initialization failure as an R condition: it writes it to the MESSAGE stream, returns an EMPTY `stanfit` (mode 2), and returns normally. The driver then degraded silently through three layers, `summary(fit, pars=)$summary` returning `invisible(NULL)` (hence the 3-byte `bss_summary_*.csv`), `quantile(NULL, ...)` returning `NA NA NA`, and finally `apply(rstan::extract(fit, "E")$E[, 1, , 1], 2, median)` on a `NULL`, which is what threw. The `bss-fits` chunk is `results='hide'`, so the one line naming the real variable was the only diagnostic emitted and the only one not displayed.
-   **Fix, part 1: forward the five fields** in both preps. No model, prior or likelihood change: with `use_osp_crab_lower = FALSE` they are `OSPF_n = 0` plus three zero-length integer arrays, which is what the neutral path of `crab_fraction_stan_data()` always returned. The 2026-08-25 batch's intended behaviour is unchanged; it simply becomes runnable.
-   **Fix, part 2: `03_R_functions/bss_stan_fit.R` (new), called by both drivers in place of `rstan::stan()`.** Same arguments, same seed, same RNG stream, so a fit that succeeds is byte-unchanged and the gear track's exact-reproduction test still means what it meant. It adds `bss_assert_stan_data()`, which parses the `data` block of the `.stan` file in use and refuses to call the sampler when a declared variable is missing, non-numeric, or non-finite; `bss_assert_fit_usable()`, which rejects an empty `stanfit` and quotes what Stan said rather than letting `NULL` propagate; and a per-fit `stan_console_<label>_att<n>.log` written to `output_dir` from a NON-muffling `withCallingHandlers()`, so sampler progress still reaches knitr while a chain failure stays diagnosable after a `results='hide'` knit.
-   **Fix, part 3: the regression test that was missing.** Section 9 of `06_diagnostics/test_improvements_2026-08-25.R` asserts, for BOTH models, that every variable declared in the Stan `data` block is built in the corresponding prep, and that every crab-fraction field is returned by EVERY return path of `crab_fraction_stan_data()` (shore/off, `f` pinned, `f` estimated). Verified to fail on the pre-fix files and pass on the fixed ones. The harness is now 80 assertions and still needs no rstan.
-   **The process point.** The 2026-08-25 batch was reported as static-checked: both Stan files parsed under stanc 2.32.2, every R module and both drivers parsed, 67 unit assertions passed. None of those crossed the R-to-Stan boundary, which is the one seam that batch changed on both sides at once. A parse check on each side of an interface is not a check of the interface.
-   **Status.** The validation ladder has NOT been run. Every number the 2026-08-25 batch claims remains unconfirmed by a fitted run.
-   Files changed: `03_R_functions/prep_bss_crab_pooled.R`, `03_R_functions/prep_bss_crab_gear.R` (the five fields); new `03_R_functions/bss_stan_fit.R`; both drivers (`bss_stan_fit()` call site); `06_diagnostics/test_improvements_2026-08-25.R` (section 9); `README-R-functions.md`; `development_notes/PIPELINE_STATUS.md`; this history.

Eight improvements requested after the 2026-08-18 FWC presentation, plus two defects surfaced while auditing items 1 and 2. Everything behaviour-changing ships OFF except the three changes that were explicitly requested. Coded and static-checked only; the validation ladder that would confirm it failed on a separate defect (see the 2026-08-26 entry) and has not yet been re-run, so **nothing below is confirmed by a fitted run**. Full rationale, evidence and the run order live in `development_notes/PIPELINE_STATUS.md`.

The v7.7 move to gear-deployments replaced `L` with `tau_shore` (a dimensionless turnover, ~1.7) but left the OBSERVATION as `ie_crabber_hours`, so since v7.7 the model has compared crabber-HOURS against a predicted crabber-TRIPS, roughly a 4x scale mismatch (~331 observed against ~80 predicted on a typical survey day). This is the most likely mechanism behind the standing unexplained shore all-gear `sigma_IE` ~1.07 (GR-9). Fixed by routing the observation through `bss_effort_spec()$ie_obs_col` (deployments -> `ie_trips`; time units -> `ie_crabber_hours`) in both preps, so the pair cannot drift again. `ie_shore_obs_unit = "crabber_hours"` reproduces the old behaviour. **This moves the shore number and must be isolated in its own run.**
-   **(B) DEFECT: shore monthly PE effort share still on crabber-hours.** `pe_monthly_effort_share.R` used the pre-v7.7 `mean_count * crabbers_per_gear * day_length` formula, re-weighting the shore monthly PE split toward long-day months. Totals were never affected (the share is normalised); the monthly split was. Now routed through `bss_effort_spec()`.
-   **(1) Gear deployments audited everywhere effort is formed**, not just the CPUE denominator: the opener-spillover diagnostic now measures CPUE per `number_of_gear`; the gear-resolved daily-combined series no longer applies the shore crabber-hours formula to the boat; the by-gear incomplete-trip bias is reported in deployments; the BSS effort plot axis and the `bss_L_effective_*.csv` `L_prior_mu` column are corrected (now `L_prior_center` + `L_unit` + a separate hours column). "Pot lift" is struck from both method documents: a deployment is a piece of gear in the water on that trip, and slot re-use is carried by `tau`.
-   **(2) Effective day length documented for what it is.** Production expands on a TURNOVER, not a day length; `L_effective` (~5.26 h) sets only a diagnostic column. Their ratio, 5.26 / 1.72 = 3.07 h against an interview-reported 3.23 h, is the method's free internal consistency check and is now stated in both documents.
-   **(3) Weekend is Saturday and Sunday.** Friday leaves `days_wkend`. Paired within month: shore log(Fri/Sat) = -0.844 (t = -8.88, p = 2.4e-06), boat -0.507 (t = -3.81, p = 0.003); against Mon-Thu, Friday is 1.21x (p = 0.10) shore and 0.99x (p = 0.96) boat. Residual variance the AR must absorb falls 15% (shore) / 5% (boat). Known residual: the boat's Sunday mean sits below its weekday mean on 5 sampled Sundays, which is a field-plan question, not a config edit.
-   **(4) Other-fishery openers as auto-selected effort covariates.** The razor-only `B3` term is generalised into a `K_open` / `X_open` / `B_open` block in both Stan models, with per-population candidate lists. `K_open = 0` is production and reproduces the previous model. `opener_covariate_mode = "auto"` screens on the spillover diagnostic's adjusted p-values after a Benjamini-Hochberg adjustment across the eight effort tests, and only where the indicator is identifiable inside the fit's window; the arbiter remains effort-stream `elpd_loo`, because selecting on a p-value then fitting the term inflates it. CPUE gets no opener covariate (all eight opener-vs-CPUE tests were null). The interaction that must not be missed: a halibut term legitimately fits the ALL-boat trailer series, but a constant `f` then converts the fitted surge to crab effort at the same rate as a closed-fishery day, so `crab_fraction_strata` gained `"opener"` / `"month_opener"` and both drivers warn when a boat opener is active without them.
-   **(5) Incomplete trips: a four-arm diagnostic; production unchanged.** `sensitivity_incomplete_trips.csv` reports `exclude` (production), `gear_only`, `impute_mean_cpue` and `keep`, with the gear ratio and a length-bias test under each. **Direct answer to the question asked: no, option 2 is not already how the model functions.** `prep_bss_crab_*()` derives `intA` from the already-filtered frame, so an incomplete trip's fully observed gear count is discarded with its truncated catch; and the two estimators disagree, since `run_pe_*()` takes the boat gear-per-group from the UNFILTERED set, so the boat PE already behaves like `gear_only` while the boat BSS behaves like `exclude`. Option 1 is a pooled no-op by arithmetic (a ratio-of-sums over complete-plus-imputed returns the complete-trip rate identically), and in the BSS it would be worse than a no-op because it adds fabricated observations that tighten the CPUE interval without adding information. The framing that bounds all four arms: effort does not come from interviews, so no treatment of incomplete trips can add effort to the expansion.
-   **(6) `bss_min_interviews` 20 -> 15.** The only component this changes is the private-boat POT CLOSURE (17 interviews), previously never fitted and entering the port total as an interval-free PE point. A second floor `bss_min_interviews_fitted` is applied AFTER zero-denominator and incomplete-trip filtering, because the pre-existing guard counts unfiltered interviews and reads looser than what the likelihood sees. Both floors moved out of each driver's `params_model` into `run_config.R`, where they belong: `params_model` is merged ON TOP of `run_config` and was silently overriding it. Honest expectation: 17 interviews over 76 days may still fail the gate, which is a better outcome than a threshold decision taken before any data were looked at.
-   **(7) AR resolution escalation ladder (`ar_escalate`, ships FALSE).** Each component starts at the finest rung, goes through the same convergence gate that decides PE-vs-BSS, and is refit one rung coarser on failure, stopping at the first pass; `ar_escalation_log.csv` records every attempt and the verdict that triggered the next. Cost stated rather than buried: each rung is a real multi-hour fit and the capped components burn their known-bad rungs first, so expect roughly 2-3x wall clock.
-   **(8) OSP crab-only counts as a HARD LOWER BOUND on `f` (`use_osp_crab_lower`, ships FALSE).** OSP does not record combo trips, so its crab-only share bounds `f` from below and is not an estimate of it; treating it as an estimate would bias the boat DOWN by exactly the combo rate, on the halibut and tuna days where that rate is highest. Structurally: `f_lower ~ Beta(1,1)`, `osp_crab_only[i] ~ BetaBinomial(osp_total[i], f_lower*kappa, (1-f_lower)*kappa)` per OSP DAY, and `f = f_lower + (1 - f_lower) * theta`. The likelihood is per day and beta-binomial, not a binomial on the stratum sum, which would treat ~7,500 boat-days as independent trials and give `f_lower` an SD near 0.005 that ~150 correlated daily observations do not support. **Identifiability, stated plainly: OSP alone identifies `f_lower`, never `theta`**; `theta` rests on the `crab_fraction_combo_share` placeholder until egress classification covers the same stratum, which is the operational reason to schedule egress days on days OSP is in port. Degradation is exact: with no OSP classification in a stratum `f_lower` is pinned to 0, `f = theta`, and R hands Stan the ordinary `f` prior. Both new terms sit on OBSERVED boat counts, so `f` stays in generated quantities only and the validated Phase 2/3 properties survive.

### v6.7 (2026-06-19), Effort overdispersion marginalized to negative binomial (B1.5)

-   Marginalized the per-observation effort overdispersion. The effort counts were modeled as a Gamma-Poisson mixture with an explicit length-`n_effort_obs` latent multiplier `eps_E_H_obs ~ Gamma(r_E, r_E)`, a high-dimensional centered latent block. Because the Gamma-Poisson mixture integrates exactly to `neg_binomial_2(mu, r)` (Hilbe 2011), the latent multipliers were removed and both effort-count likelihoods rewritten directly as negative binomial. The marginal likelihood is identical, so the change is inference-preserving; it removes the centered latent block, improves mixing (n_eff rose materially on several fits), and makes the model block consistent with the `log_lik` block and the interview-catch likelihood, which already used the marginal form. `n_effort_obs` is retained in the Stan data block as an unused field to avoid breaking the R prep interface.
-   Outcome: estimates were unchanged within Monte Carlo noise (inference preservation confirmed) and mixing improved, but the residual shore divergences did not clear, which localized the divergence source away from overdispersion and motivated the v6.8 diagnostic and gate.

### v6.6 (2026-06-17), Non-centered AR initial state (B1.3)

-   Non-centered the AR(1) initial states `omega_E_0` and `omega_C_0` in `crab_bss_pooled.stan` and in the augmented `crab_bss_pooled_weather_adjusted.stan`. They previously carried a centered prior `normal(0, sqrt(sigma_eps^2 / (1 - phi^2)))` whose scale is a function of the sampled parameters `sigma_eps` and `phi`, which is a textbook funnel (Betancourt and Girolami 2015). They are now declared as raw standard-normal parameters (`omega_*_0_raw`) and scaled by the stationary SD in the transformed-parameters block, so the implied prior is identical and the posterior is unchanged while the sampling geometry no longer funnels. No Jacobian adjustment is required because the prior is placed on the raw parameter, not on a transform of a parameter.
-   Motivation: the v6.5 run (2026-06-17) showed that the AR cap improved boat mixing (R-hat 1.07 to 1.01, n_eff 76 to 261) but did not clear the divergences. All three fitted components failed the gate and fell back to PE. The divergence signature pointed to a centered funnel rather than latent dimension: `treedepth_pct` 0 across every fit, roughly 98% divergence on the boat, and persistence at `adapt_delta` 0.99 (which controls step size and cannot fix a funnel). `omega_0` was the dominant remaining centered parameter; the AR innovations, `L`, and the hierarchical intercepts were already non-centered.
-   Honest expectation: this is the correct fix for the funnel and should help all three fits, but a roughly 98% boat divergence rate is severe and the trailer-count effort series is weakly informative, so the boat is not guaranteed to converge on this change alone. If it still fails, the remaining levers are inference-changing decisions (a tighter `sigma_eps` prior, monthly boat AR, or accepting PE for the boat) rather than reparameterizations.
-   Files changed: `crab_bss_pooled.stan` and `crab_bss_pooled_weather_adjusted.stan` (both: `omega_*_0` reparameterization, header note); `BSS-GH-pooled-CPUE-model.Rmd` (header version only); this documentation (Sections 10, 14). There is no R code change; the reparameterization is internal to the Stan model.

## Appendix A: B1.5 working notes (v6.7), marginalizing the effort-count over-dispersion

These are the consolidated working notes behind the v6.7 entry, preserved for provenance. They supersede the standalone `B1.5_change_notes.md`.

**The problem.** The residual shore divergences that survived the B1.3 non-centering (292 and 573 in the v6.6 pooled run, with otherwise clean R-hat and n_eff, and a 292-vs-1669 seed instability) came from the per-observation effort over-dispersion, not from the AR scale priors. In the model block, each effort count was written as a Gamma-Poisson mixture:

```stan
eps_E_H_obs[i] ~ gamma(r_E, r_E);                  // n_effort_obs of these
Gear_I[i] ~ poisson(lambda_E * eps_E_H_obs[i] * R_G);
T_I[i]    ~ poisson(lambda_E * eps_E_H_obs[Gear_n + i] * R_T);
```

`eps_E_H_obs` is a length-`n_effort_obs` vector of latent parameters whose distribution depends on `r_E = 1 / sigma_r_E^2`. That is a centered, high-dimensional funnel (311 parameters for shore all-gear, 52 for ring-net), structurally the same problem B1.3 fixed for `omega_0`, with the neck at large `r_E` / small `sigma_r`. B1.3 had non-centered the AR path and `omega_0`; this over-dispersion block was the remaining centered piece, so it was where the residual divergences lived.

**The fix.** An exact analytic marginalization. A Gamma-Poisson mixture with `eps ~ Gamma(r, r)` integrates out to Negative Binomial 2:

```stan
Gear_I[i] ~ neg_binomial_2(lambda_E * R_G, r_E);
T_I[i]    ~ neg_binomial_2(lambda_E * R_T, r_E);
```

mean `lambda * R`, variance `lambda*R + (lambda*R)^2 / r_E`. `r_E` is unchanged, so the over-dispersion is identical. The marginalization is exact, so the posterior over every reported quantity (E_sum, C_sum, C_expected_sum, B1, B2, B1_C, R_G, R_T, L, ...) is the same up to Monte Carlo noise; the only thing removed is the `n_effort_obs` nuisance parameters and their funnel.

**Why marginalization rather than a prior swap.** Three reasons: it removes the actual funnel by construction, instead of reshaping a prior on `sigma_r` whose funnel neck is at small `sigma_r` (where a half-normal would not help and could pull toward the neck); the interview catch likelihood already used `neg_binomial_2(.., r_C)` and the augmented file's `log_lik` already used the marginal form for the effort counts, so the model block was the only place left on the conditional Poisson form, and this change made the three consistent; and it resolved the conditional-versus-marginal LOO issue, since with the per-observation random effects gone the model block and `log_lik` are the same form, putting the PSIS-LOO comparison on solid ground (Vehtari, Gelman, and Gabry 2017). `n_effort_obs` was retained as an unused data field so the R prep did not need to change.

**Outcome.** Estimates were unchanged within Monte Carlo noise (inference preservation confirmed) and mixing improved, but the residual shore divergences did not clear, which localized the divergence source away from over-dispersion and motivated the v6.8 diagnostic and gate. The boat was unchanged by this edit; its non-convergence is weak identification from the trailer-count series, not this funnel.

## Appendix B: B1.6 working notes (v6.8), proper sigma_IE prior and the distortion-aware gate

These are the consolidated working notes behind the v6.8 entry, preserved for provenance. They supersede the standalone `B1.6_change_notes.md`. The distortion-aware gate described here was itself later superseded by the v7.0 scale-aware gate (see the v6.8 and v7.0 version-log entries); these notes are retained because they document the diagnostic reasoning that justified moving shore onto the BSS.

**What the divergence diagnostic showed.** Run on the three v6.7 fits, the diagnostic split cleanly into a shore story and a boat story.

- **Shore (ring-net 5.0%, all-gear 4.0% divergences).** No funnel neck. The largest standardized separation between divergent and bulk draws was 0.44 (ring-net, on `sigma_IE`) and 0.20 (all-gear, on `sigma_mu_E`). A real funnel shows a standardized separation well above 1 with divergent draws jammed into a tail; nothing here did. The divergences were diffuse low-grade curvature, not a single reparameterizable neck, which is why B1.3 and B1.5 had not moved them. And the distortion check was decisive: dropping the divergent draws shifted the totals by +0.7% / -0.1% (ring-net) and +0.4% / +0.2% (all-gear). The shore estimates did not depend on the divergent draws. For shore, the gate, not the geometry, was forcing PE.
- **Boat (97.2% divergences).** A genuine bug, caught by the diagnostic: `sigma_IE` sat at the floating-point ceiling (about 1e307). The boat has no I/E observations (`IE_n = 0`), and the prior on `sigma_IE` was inside `if (IE_n > 0)`, so for the boat `sigma_IE` had no prior and appeared in no likelihood, an improper flat direction. That breaks mass-matrix adaptation and sprays divergences across the trajectory. The boat already passed R-hat (1.0067) and n_eff (555/1281); much of its divergence count was this artifact, not a broken effort posterior.

**The sigma_IE fix.** `sigma_IE ~ exponential(5)` was moved out of the `if (IE_n > 0)` block so it is applied unconditionally; the I/E likelihood stays gated on `IE_n > 0`. Because `sigma_IE` is decoupled from effort and catch, this cannot change the boat's effort/catch target; it only makes the posterior proper and the sampler well-behaved. Applied to both `crab_bss_pooled.stan` and `crab_bss_pooled_weather_adjusted.stan`.

**The distortion-aware gate (since superseded by v7.0).** Two clean reparameterizations had not cleared the shore divergences, the diagnostic showed no funnel neck to target, and the distortion check showed the divergences did not move the shore totals. The defensible move was to make the gate test what matters, whether the divergent draws corrupt the estimate, instead of a raw count: a fit exceeding `max_divergences` could still pass if it was otherwise clean (R-hat, n_eff, treedepth) and its divergent draws did not move `C_expected_sum` or `E_sum` beyond `max_divergence_distortion` (default 0.02, a fractional shift). Expected effect: shore ring-net and shore all-gear move from PE to BSS (both shift under 1%); the boat fails the distortion test (catch shift about 3.7%) and stays PE. The stated caveat was that the distortion check is a practical safeguard, not a proof of unbiasedness (if the sampler avoided a region, divergent and non-divergent draws could share a bias); the justification for adopting shore was the conjunction of clean R-hat / n_eff / treedepth, estimates stable across B1.3, B1.5, B1.6 and across seeds, and non-distorting divergences. v7.0 later replaced the level-normalized distortion (which scales with posterior width) with an SD-normalized impact (which does not), because the level form was failing the boat for being weakly identified rather than biased.

**The single-group hierarchy redundancy, noted here, addressed later.** The diagnostic's top shore all-gear correlate was `sigma_mu_E`. In the pooled model G = 1 and S = 1, so the intercept is built as `mu_E[1,1] = mu_mu_E[1] + eps_mu_E[1,1] * sigma_mu_E`: three parameters for one identified quantity, which the likelihood sees only as their sum, so `sigma_mu_E` and `eps_mu_E` trade off in a mild funnel. This is a genuine over-parameterization for the single-group pooled model (it is meaningful only when G > 1, the gear-resolved track) and a mild divergence contributor, not the cause. The obvious collapse (`mu_E[g,s] = mu_mu_E[g]`) was attempted as B1.7 in v6.9 and reverted after it hung the shore all-gear fit; see that version-log entry. The durable lesson, reaffirmed across this appendix and the v6.9 and v7.4 entries, is that the boat's non-convergence is weak identification from a thin effort series, and the remedy is a more informative effort series rather than further parameter surgery on the shared model.
