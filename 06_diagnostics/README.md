# 06_diagnostics

**The validation harness and the dated batch runners.** Nothing in this folder is a production estimator; the estimate comes from the drivers in `01_BSS_models/`. What lives here is the machinery that decides whether a change to those drivers is safe and worth keeping:

- `test_improvements_2026-08-25.R`, the dependency-light regression harness. Run it before committing to any long fit; it prints its assertion count at the end (**1,420 assertions** as of 2026-09-29, all passing; the harness checks that this figure never exceeds the count it runs). Since 2026-09-29 (D37) a check whose committed input is missing prints `SKIP` and is counted apart on the summary line (`passed, failed, skipped`); it used to pass silently, so on a full checkout the skip count should be 0.
- `run_*.R`, one dated batch runner per validation campaign. Each dated batch runner ships `DRY_RUN <- TRUE` (asserted by the harness for every runner that has the switch), resolves every stage's config and runs its pre-flight without fitting, is resumable, and writes its pass/fail verdicts to a `*_verdicts.csv` at the `05_output/` root. (`run_rg_sweep.R` is the exception: a sensitivity sweep, not a ladder, it is not resumable and writes `rg_sweep_<date>_summary.csv` instead.) The convention that grew out of hard experience: pre-set the pass criteria in code BEFORE the run; compare per-fit summaries for exactness, never port totals (permuted draws move a port total ~0.2% between bit-identical fits); expect a config delta of exactly the keys the stage changes (`config_delta`); wrap every verdict block so a defect in the READING of a run can never destroy the run's output. **Two `run_*.R` files have no `DRY_RUN` switch:** `run_osp_validation.R` and `run_tau_sweep.R`, which refuse to fit (superseded; B31 and B46). (`run_rg_sweep.R` gained one on 2026-09-28, B49.) Every guarded runner fails closed: when the guard file cannot be found it stops rather than running. The desk screen and `gear_coverage_audit.R` fit nothing and need none.

**TWO KINDS OF RUNNER, AND THE DIFFERENCE MATTERS (2026-09-13).** A static audit asked how
many of the fifteen levers that define Method v2.0 each runner PINS or SETS:
`run_improvements_2026-09-08.R` pins 12 of 15, because B22 gave it a `WINDOW` pin and a
preflight that FAILS on any undeclared difference between rungs;
`run_gear_ar_zi_2026-09-13.R` pins the same way; every runner written before 2026-09-08
pins 0 to 5. All of them still parse and all of them still complete. **That is what makes
the old ones dangerous rather than merely stale**: a runner that does not pin the dynamic
`f`, the calibrated turnovers and the census split will fit its "pre-patch baseline" rung
with today's values and label the result as the earlier state, and nothing in its output
will say so. A broken runner announces itself; this class does not.

**THE LIVE LADDERS CANNOT RE-FIT THEIR COMMITTED RUNGS BIT FOR BIT ANY MORE (2026-09-29 sweep).** `run_improvements_2026-09-08.R`, `run_gear_ar_zi_2026-09-13.R` and `run_marine_hazard_batch_2026-09-25.R` start from `BASE <- run_config`, and their `WINDOW` pins do not cover the changes that reached the data on 2026-09-28: the Float 17-21 fill (`shore_f17_fill`, B45; about +9% on the shore gear count), the ISO-week periods (B46, a code change no key can pin), the interview-id repair (B44), the initial-value radius (`bss_init_r`, B51) and the single-section level collapse (`mu_hier_collapse_single`, A31, 2026-09-29), which changes every pooled fit. A rung fitted now therefore uses different shore data and different chain starts than the committed rung RESUME reuses, so a re-fit of G1 or M1 cannot be bit-identical to its reference. The runners detect it (a REVIEW row from the code and inputs fingerprints; the NOT-equivalent records in `CODE_NOT_EQUIVALENT` and `CODE_NOT_EQUIVALENT_MH`), but read any new rung against a new baseline rendered on the same tree, not against the committed folders. This matters for D3, which its row calls one render from closed.

So the nine runners whose question is CLOSED now **refuse to fit and are kept to be read**
(`03_R_functions/bss_superseded_runner.R`; set `I_KNOW_THIS_IS_SUPERSEDED <- TRUE` to
override, having read why you should not). They are not deleted: each is cited by 7 to 15
documents and by the harness, each records how a decision was reached, and the 20260825
output folders carry no `run_parameters.txt` at all, so `run_patch_validation_2026-08-25.R`
is the only surviving description of what they were configured as. **LIVE** and **RECORD**
in the table below say which is which.

Each runner's row below records whether it has run and where its results were reviewed. **For where the model currently stands**, read the box at the top of `07_documentation/development_notes/PIPELINE_STATUS.md` and the change register `07_documentation/development_notes/CHANGE_REGISTER.md`.

For the production models, see [`01_BSS_models/`](../01_BSS_models/README.md); for the project overview, the [root README](../README.md).

## The weather-tide covariate module: REMOVED 2026-09-13

It used to live here, and this section is what replaces it so nobody goes looking.

**Removed** (CHANGE_REGISTER A29): the driver `BSS-GH-pooled-CPUE-weather-tide-covariates.Rmd`,
its Stan fork `02_stan_models/crab_bss_pooled_weather_adjusted.stan`, the `run_weather` toggle
and the `--weather` / `--no-weather` flags. `run_estimation.R` stops with a message if either flag
is passed (since B46, 2026-09-28, it stops on any argument other than `--model`).

**Why.** The FWC creel team advised against using weather covariates and weather on its own was
not helpful. The module's own committed conclusion was already EXCLUSION: tide phase and range,
daytime high-tide timing, wind and wave height were screened on both effort and catch rate and
none cleared the pre-committed PSIS-LOO margin. Two practical facts settled it rather than
continued carrying: the fork had drifted about **40 data variables** behind the production model
(missing the whole `shared_tau` block, the OSP stream, the `crab_fraction_*` block and the
zero-inflation flags), so it could not have been run without a re-base; and nothing depended on
it, with no production driver, config key or helper referencing the fork and no committed run
folder produced by it.

**Where the record lives.** The finding is
`07_documentation/WEATHER_COVARIATE_ANALYSIS.md`, kept in place because it is a decision record;
the module's method document is archived at
`07_documentation/archive/weather-tide-covariate-module-REMOVED.md`; and Method v2.0 states the
conclusion in its Section 21. Read the false-precision result in the finding before running any
future covariate screen on this pipeline: the apparent signal came from comparing a covariate
model's `elpd_loo` against the SE of ONE model total rather than the PAIRED SE of the
difference, and that mistake is not specific to weather.

**Not the same thing, and not removed:** the OTHER-FISHERY opener covariates
(`opener_covariate_mode`, `run_config.R` section 4.3). Built, tested, inert, still available.

**Also not the same thing (2026-09-25):** the MARINE HAZARD covariates (`marine_hazard_mode`
and the flag definition in `run_config.R` section 2.10, the method of record since 2026-09-27;
the experiment surface in section 4.4b; `run_marine_hazard_batch_2026-09-25.R` above). The removed module
screened continuous weather and tide (wind speed, wave height, tide phase) in its own Stan fork;
these are the NWS's own binary hazard decision (archived, known on every day) and the Coast Guard's
bar closure (the samplers' tick, observed on sampled days and imputed on the rest), riding on the
production model's existing opener block with no fork. The
paired-SE lesson from the finding is written into that runner's rule.
